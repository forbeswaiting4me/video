# WB Полки — кто стоит рядом с товаром

На карточке WB покупатель видит не только товар, но и десятки чужих карточек в блоке
«Смотрите также» (и «С этим товаром покупают»). Селлеры вылизывают карточку и ни разу не
смотрят, кого им туда поставил аукцион полок. Этот скилл смотрит — и отдаёт результат
в том же виде, в каком его показывает раздел «Мониторинг полок» MarketGuru, только по всей
линейке сразу и с расчётом двух утечек.

Два вопроса:

1. **Кто стоит рядом с моими карточками** — чей товар забирает моего же покупателя.
2. **На чьих карточках стою я** — откуда идёт чужой трафик ко мне, на каком месте, за деньги или органикой.

## Источники — какой что показывает (главное, читать первым)

| Ручка MPStats | Что это | Роль |
|---|---|---|
| `POST analytics/v1/wb/items/{nm}/recommended` | **Снимки реального блока «Смотрите также»** по дням: `positions: {дата: {position, ads, cpm}}` | **Основа обоих карт.** Это и есть «полка» в терминах MarketGuru |
| `in_similar/items` | Обратный индекс: карточки, где наш товар показан как похожий, с выручкой донора | Список доноров и их вес. **Не факт показа** |
| `similar/items` | WB-модель соседства по предмету | Вторая база для пустых доноров. В первый экран не идёт |
| `identical`, `identical_wb` | AI-модели почти-дублей | Только для поиска каннибализации своих карточек |

**Не путать модель и факт.** `similar` для предмета «Перчатки спортивные» тянет мембранные
и мотоперчатки — 1 000–2 000 SKU, это модель. Полка героя по `recommended` — 40–1 900 SKU
с датами и позициями, это факт. Утечки, матрица и воры считаются **по `recommended`**;
`similar` пишется в отчёт как «модель соседства MPStats», не как «на вашей карточке стоят».

**Позиция на чужой полке берётся только из снимка полки донора**: `recommended` по nm донора
→ поиск своих nm в `data[]` → `positions`. `in_similar` даёт список доноров, но не позиции.
MarketGuru показывает именно это — таблицу «донор × наша позиция по дням».

Ответ `recommended` содержит только `id, name, price, price_min, price_max, revenue, sales,
sales_graph, thumb, positions` — рейтинга и продавца там нет, обогащать отдельно.

## Что скилл НЕ может

- **Блок «С этим товаром покупают» через MPStats недоступен.** Только режим Замер (браузер).
- **Один снимок в день ≠ частота показа.** Полка персонализирована. `shelf_share` считается
  только в режиме Замер; по MPStats — доля замеров, и подписывать её так.
- **Карточку WB из облака не открыть** (`498`), `search.wb.ru` — `429` со второго запроса.
  `card.wb.ru/cards/v4/detail` из облака **доступен** — им обогащаем цены и рейтинги.
- **В рекламе WB нельзя выбрать карточку-донора.** Управляем только размещением
  `recommendations`, ставкой и карточкой.
- **Срезы `similar/sellers`, `/brands`, `/price_segmentation` на обычном тарифе — `403`.**
  Продавцов и ценовые полосы считаем сами по строкам.
- **Три исхода запроса, не смешивать:** `total: 0` → «соседей не найдено»; ошибка/`401` →
  «сбор не сработал»; `429` → «лимит MPStats». Обрыв прокси (пустой ответ, не-JSON) — повтор,
  а не «нет данных».

Деньги по полкам — из `sellego-api` (`placementType=3`). Нет токена — отчёт показывает
соседство без рублей, и это пишется на первом экране.

## Онбординг

По одному вопросу, кнопками. Ответы в `.wb-polki/settings.json`.

1. **Токен MPStats** — обязателен. Сначала проверь тот, что уже есть в проекте/памяти:
   `GET api/user/report_api_limit` (`account-limits.sh`). `401` — просить новый, не изображать
   работу. Передавать **переменной окружения** `MPSTATS_TOKEN` в вызове; `config/.env` скилла
   `mpstats` перебивает инлайн-токен — проверь, что его там нет.
2. **Артикулы.** Если в проекте есть прошлые прогоны — предложи тот же набор кнопкой
   («сравнение с прошлым срезом»). Больше 20 за прогон не брать. «Весь кабинет» — список из
   `analytics/v3/sales-funnel/products` (фильтр `nmIDs` игнорируется, приходит весь кабинет).
3. **Токен Sellego** — опционально.
4. **Замер нужен?** По умолчанию нет.

Пользователь написал «без вопросов, я отошёл» — дальше не спрашивать, брать разумные
дефолты и подписывать их в отчёте.

## Сбор — режим Карта

Все запросы `fbs=1` — при `fbs=0` FBS-кабинеты занижаются в десятки раз. Период — 30 дней,
`d2` = вчера. Сортировка `revenue desc`. **Окно `endRow − startRow ≤ 500`** (иначе `422`) —
пагинировать.

```bash
# 1. Модели: similar / in_similar по каждому герою (скрипт скилла mpstats)
MPSTATS_TOKEN=… wb-similar.sh similar    <nm> products <d1> <d2> 500 1 > .wb-polki/map/similar-<nm>.json
MPSTATS_TOKEN=… wb-similar.sh in_similar <nm> products <d1> <d2> 500 1 > .wb-polki/map/in_similar-<nm>.json

# 2. Факт: полка героя, все страницы по 500
POST https://mpstats.io/api/analytics/v1/wb/items/<nm>/recommended?d1=&d2=&fbs=1
     {"startRow":0,"endRow":500,"filterModel":{},"sortModel":[]}   → .wb-polki/shelf/rec-<nm>-p<N>.json
```

Запросы оборачивать в повтор: до 5 попыток, проверка, что тело — валидный JSON; `429` →
`Retry-After` или 20 с. Прокси облака рвёт длинные ответы («ws_closed_mid_exchange») —
это повтор, не ошибка данных. Длинные серии — фоновым процессом с логом, не в одном
вызове шелла (лимит 2 минуты).

**3. Обогащение** — `card.wb.ru/cards/v4/detail?appType=1&curr=rub&dest=-1257786&nm=a;b;c`
(разделитель **`;`**, батч 50): `sizes[].price.product/100` — цена с СПП, `reviewRating`,
`feedbacks`, `supplier`, `supplierId`. Обогащать только соседей с `revenue > 0` (остальные
имеют нулевой вес) плюс свои карточки. **Свои и чужие цены — из одного источника**;
цена из кабинета (`discounts-prices`) против витринной даёт ложную утечку 80 %+.

**Свои карточки = все с нашим `supplierId`** из ответа card.wb.ru, а не только герои прогона:
на полках героев стоят младшие артикулы кабинета, и без этого «свои рядом» не посчитать.

**4. Полки доноров** (карта 2, формат MarketGuru). Список: объединение топ-30 `in_similar`
по выручке и топ-25 соседей полки по каждому герою, минус свои, ≤ 120 карточек. По каждой —
`recommended` со всеми страницами, ищем свои nm. Бюджет: ~1–2 запроса на донора, 40 с на
донора через прокси — 120 доноров ≈ 1 час фоном. Остаток квоты — `available_wb_external`
из `report_api_limit`, смотреть до старта.

**5. Медиана предмета** — `subject/items` по `subject_id` героя, но **сначала посмотреть
топ-10 предмета**: если предмет широкий (десятки тысяч SKU, топ из другого товара — как
«Перчатки спортивные» с хоккеем в топе), база непригодна, и это пишется в методологию.
Тогда порог «слабый донор» — медиана выручки доноров `in_similar` с выручкой > 0 по всем
героям, «сильный» — фиксированный порог (50 тыс ₽ за период), оба подписаны.

## Метрики

**Утечки — по полке героя (`recommended`), взвешенно по `revenue` соседа**, соседи с нулевой
выручкой в знаменатель не входят. Рядом — та же доля по числу замеров слотов (в скобках).

```
ценовая утечка        Σ revenue чужих соседей с ценой < моей / Σ revenue чужих соседей
рейтинговая утечка    то же для рейтинга > моего при ≥ 50 отзывах
реклама на полке      замеров с ads=1 / всех замеров
свои на полке         замеров своих nm / всех замеров; по каждому своему — замеров и лучшая позиция
медиана цены соседа   по соседям с выручкой; разрыв с моей ценой — главный аргумент «резать/не резать»
```

**Не складывать** ценовую и рейтинговую утечку — «ИЛИ» даёт 60–70 % у кого угодно.

**Метрики MarketGuru «Мониторинг полок» — по снимкам доноров, на каждый свой артикул:**

```
Кол-во полок (всего)        доноров в in_similar (индекс — модель)
Кол-во полок (подтверждено) доноров, в чьём снимке наш nm найден
Кол-во полок в ТОП-10 / ТОП-100   по медиане позиции у донора
Ср. позиция за 7 дней        медиана позиций за последние 7 дат снимков
Распределение по ТОПам       Топ 1 / 5 / 10 / 30 / 60 — число полок
Новые / Выпали               донор впервые появился / последний раз виден за 7 дней до d2
Рекламных позиций            доля снимков с ads=1
Динамика ТОПов               по дням: полок всего и в ТОП-10 (столбики)
```

Присутствие у доноров считать **по счёту подтверждённых снимков**, а не по доле выручки
«выше медианы» — последняя всегда 90 %+ и ничего не значит.

**Режим Замер** — и только он: `shelf_share`, `avg_slot`.

## Четыре типа находок

| Тип | Что это | Действие |
|---|---|---|
| **Воры** | сосед на полке героя в топе по выручке, дешевле или с лучшим рейтингом | `wb-card-roast`; цена и рейтинг важнее ставки. Если вор из другого ценового класса (в 2 раза дешевле) — отстройка первым фото, не ценой |
| **Пустые доноры** | сильная карточка (≥ порога), чей снимок снят, а нас в нём нет — плюс сильные карточки `similar`, которых нет в `in_similar` | включить `recommendations`, поднять ставку через `wb-promotion`, повторить снимок тех же доноров через 7 дней |
| **Свои рядом** | свои nm на полке героя (по `supplierId`) | дополняющие — хорошо; дубли дешевле героя — схлопнуть; сравнить цены своих на одной полке |
| **Слабые доноры** | в `in_similar` 60–75 % доноров с нулевой выручкой | не радоваться «мы в сотнях полок», целевые — только сильные |

## Отчёт — формат «Мониторинг полок» (HTML, стиль `mpstats/references/presentation.md`)

Порядок блоков фиксированный, чтобы отчёт читался как экран MarketGuru:

1. **Шапка**: кабинет, период, число артикулов, источник полки (`recommended`), база
   порогов, есть ли Sellego. Без этих подписей цифры первого экрана не показывать.
2. **KPI**: ценовая утечка · рейтинговая утечка · реклама на наших полках · свои на своих
   полках · присутствие у доноров (подтверждено / проверено). Плюс callout «Главное» — только
   вычисленные числа, никаких вбитых руками.
3. **Таблица по артикулам**: наша цена · полка SKU/замеров · реклама % · свои (%) · две утечки
   (по выручке, в скобках по замерам) · медиана цены соседа · доноры всего / 0 ₽ / сильных.
4. **Матрица соседства** — строки свои артикулы, столбцы: сначала свои (зелёные), потом
   топ соседей по сумме замеров; подпись столбца — `продавец · nm`, не название товара
   (у соседей одинаковые названия). Ячейка — замеров, интенсивность по строке.
5. **Топ-10 воров** с картинками (**thumb → data-URI**, внешние картинки в артефакте
   блокируются), цена, рейтинг, разница с нами, на каких полках, замеров, лучшее место.
6. **Ценовая полоса** — доля выручки соседей по полосам, наша полоса выделена.
7. **Мониторинг полок** (MarketGuru): таблица «всего / подтверждено / ср. позиция 7 дн /
   Топ 1-5-10-30 / новые / выпали / рекламных» по каждому герою и столбики «Динамика ТОПов».
8. **Позиции по полкам**: донор (название, продавец, выручка, цена/рейтинг, размер полки) ×
   наши карточки на его полке — дней · медиана позиции · лучшая; позиция **фиолетовая** —
   реклама, **зелёная** — топ-5 органикой (как в MarketGuru: без цвета — органика, фиолетовый —
   реклама). Ниже — «Пустые доноры» и callout «Слабые доноры».
9. **Свои рядом**, **Продавцы на полках** (замеры, доля, SKU, выручка), **Приоритеты**,
   **Методология** со статусами каждого запроса по трём исходам.

Обе темы (светлая/тёмная) через токены; Manrope; зелёный `#17BF50`, реклама — фиолетовый
`#5B3FA3/#E9E4F5` (единственное исключение из палитры, взято у MarketGuru как условное
обозначение рекламы).

**Excel** (`xlsx`): `Сводка` (утечки — формулами `SUMIFS` по листу соседей, не числами),
`Соседи у меня` (со столбцом «Выброс» по правилам `mpstats`: цена > 3× или < ¼ медианы полки,
выручка без продаж, рейтинг 0 при отзывах — строки помечать, не удалять), `Я на чужих`,
`Позиции по полкам`, `Пустые доноры`, `Сырые ответы` (файл, дата, `total`, строк, статус),
`Методология`. Прогнать `recalc.py`, сверить формулы с расчётом в python — они обязаны
совпасть до десятой.

Отчёт публиковать артефактом (пользователь возвращается к нему и сравнивает срезы),
файлы — в выходную папку, ключевые цифры и методические грабли — в проект
(`claude/wb-polki-<кабинет>-<дата>.md`), чтобы следующий прогон сравнивал с прошлым.

## Рабочая папка

```
.wb-polki/
  settings.json                 артикулы, режим, наличие токенов
  req.sh                        POST к MPStats с повторами
  map/similar-{nm}.json         модель соседства
  map/in_similar-{nm}.json      обратный индекс
  shelf/rec-{nm}-p{N}.json      снимки полки героя (страницы по 500)
  shelf/neighbours-{nm}.json    соседи с обогащением и флагами cheaper/better
  donors/rec-{nm}-p{N}.json     снимки полок доноров
  cards.json                    card.wb.ru: цена, рейтинг, продавец
  subject-{id}-top.json         топ предмета (если база пригодна)
  donor_positions.json          позиции своих на чужих полках + метрики MarketGuru
  findings.json                 всё посчитанное
  shelf-dom.md, rounds/         только режим Замер
```

В папки скиллов не писать — синхронизация их перезапишет. Токен — только переменной
окружения.

## Режим Замер — браузер, только по запросу

Источник — карточка WB на машине пользователя (`preview_start` → скролл → `read_page`).
Первый прогон — разведка: заголовки блоков, селекторы (`.mainRecBlock--*`,
`article.product-card[data-popup-nm-id][data-card-index]`, ссылка с `targetUrl=MI`),
XHR при появлении блока, в `.wb-polki/shelf-dom.md`. Блоков нет — стоп, не серия.
Меньше 5 замеров — выводов о частоте не делать.

## Размещение в рекомендациях (wb-promotion), сверено 2026-09-09

| Действие | Ручка | Поле |
|---|---|---|
| Включить/выключить | `PUT /adv/v0/auction/placements` | `placements: {search, recommendations}` — оба обязательны |
| Ставка | `POST /api/advert/v1/bids` | `placement: "recommendations"` или `"combined"` |
| Создать РК | `POST /adv/v2/seacat/save-ad` | `placement_types: ["search","recommendations"]` |
| Мин. ставка | `POST /api/advert/v1/bids/min` | `placement_types: ["search","recommendation","combined"]` |

Единственное число `recommendation` — только в мин. ставках и фильтрах. В `auction/placements`
и `bids` — `recommendations`, иначе `400`.

## Мониторинг

Тренд без крона: повторный прогон по тем же героям и **тому же списку доноров** через 7 дней —
блок «Новые / Выпали» и сравнение с прошлым срезом из проекта. `by_date` / `compare`
на `similar` — только для модели, полку они не показывают. Плановую задачу ставить через
scheduled tasks: в промпт — артикулы, токены, режим; машина пользователя нужна только
в режиме Замер, режим Карта работает в облаке сам.

## Границы

Скилл читает и считает. Ставки — `wb-promotion`, стратегия — `wb-ads-strategy-picker`
(S6 «Защита от конкурента»), разбор против вора — `wb-card-roast`, деньги — `sellego-api`,
запросы — `mpstats`. Сколько покупателей ушло к соседу — не видно ни из какого источника;
говорить о долях и приоритетах, рубли оставить Sellego.

## Порядок прогона

1. Проверить токен MPStats (`report_api_limit`), онбординг → `settings.json`.
2. `similar` + `in_similar` по героям → `map/`; статус каждого запроса.
3. `recommended` героев со всеми страницами → `shelf/`.
4. card.wb.ru по соседям с выручкой + своим → `cards.json`; свои = по `supplierId`.
5. Список доноров → фоновый сбор `recommended` доноров → `donors/`; пока идёт — считать
   остальное.
6. Топ предмета → пригодна ли база; иначе пороги по выборке, подписать.
7. Утечки, матрица, воры, полосы, продавцы, четыре типа находок → `findings.json`;
   позиции на чужих полках и метрики MarketGuru → `donor_positions.json`.
8. HTML (артефакт) + Excel (`recalc`, сверка формул), запись в проект.
9. Замер — отдельно, только по запросу.

Готовых python-скриптов в скилле нет: выгрузка — шелл-скрипты `mpstats` плюс `req.sh`
с повторами, расчёт и отчёт пишутся в рабочей папке прогона. Не ссылаться на несуществующие
файлы и не делать вид, что они запускаются.
